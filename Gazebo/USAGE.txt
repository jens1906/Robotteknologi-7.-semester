Go2 Gazebo Simulation — Usage Guide
======================================

WHAT THIS IS
  Unitree Go2 simulation in Gazebo Jetty + ROS2 Lyrical that presents the same
  ROS interface as the physical Go2, so robot code runs on it unchanged.
  The reference is a bag recorded on the robot: go2_all_topics_6_10_11_28/.
  - Sensors on the real robot: Unitree L1 lidar (+ its IMU), head camera,
    body IMU, plus the front RealSense D455 (on the robot, not in that bag)
  - Same topic names, message types/layouts, frame ids and rates as the robot
  - Driven through the sport API (/api/sport/request), like the robot

MODEL SOURCE
  URDF and meshes from official Unitree repository:
  https://github.com/unitreerobotics/unitree_ros (robots/go2_description/)
  Vendored (copied into this repo) at upstream/unitree_ros/


PREREQUISITES (Linux)
  - Docker Engine + Docker Compose v2
  - Optional: nvidia-container-toolkit (only for the NVIDIA GPU override)
    Install: https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/install-guide.html
  - X11 display (for Gazebo GUI)


FIRST-TIME SETUP
  # Clone the repo:
  git clone <repo-url>
  cd Robotteknologi-7.-semester

  # Allow Docker to use your display:
  xhost +local:docker


BUILD
  cd Gazebo/
  docker compose build


RUN
  xhost +local:docker
  docker compose up


EXPECTED STARTUP SEQUENCE
  1. Gazebo Jetty window opens (empty world)
  2. Go2 robot spawns in the world at z=0.4m
  3. Robot drops to ground and stands up (CHAMP controller)
  4. All robot topics become available after ~5 seconds

  If the robot falls over on startup: this is normal on first run while
  CHAMP's initial stance phase settles. It self-recovers.


ROBOT INTERFACE (what robot code sees)
  go2_robot_emulator turns Gazebo data into these topics. Messages are stamped
  with wall-clock time, like the robot, and the emulator runs on wall-clock
  time, so robot code needs no use_sim_time.

  Topic                       Type                          Rate    Frame
  /lowstate                   unitree_go/LowState           450 Hz
  /sportmodestate             unitree_go/SportModeState     260 Hz  velocity body-frame
  /lf/lowstate, /lf/sportmodestate                          18 Hz
  /utlidar/robot_odom         nav_msgs/Odometry             130 Hz  odom -> base_link
  /utlidar/robot_pose         geometry_msgs/PoseStamped     17 Hz   odom
  /utlidar/imu                sensor_msgs/Imu               250 Hz  utlidar_imu
  /utlidar/cloud              sensor_msgs/PointCloud2       15 Hz   utlidar_lidar, ~4150 pts
  /utlidar/cloud_base         sensor_msgs/PointCloud2       15 Hz   base_link, robot body removed
  /utlidar/cloud_deskewed     sensor_msgs/PointCloud2       15 Hz   odom, last 3 frames
  /utlidar/lidar_state        unitree_go/LidarState         4.5 Hz
  /frontvideostream           unitree_go/Go2FrontVideoData  2x15 Hz H.264, 360p + 720p
  /api/sport/response         unitree_api/Response          one per request
  /camera/camera/color/image_raw (+camera_info)             30 Hz   camera_color_optical_frame
  /camera/camera/depth/image_rect_raw (+camera_info)        30 Hz   16UC1 mm, camera_depth_optical_frame

  Sport API (/api/sport/request):
    1008 Move {"x","y","z"}  clamped to 0.6 m/s, 0.4 m/s, 1.6 rad/s
    1003 StopMove
    1005 StandDown, 1001 Damp                         lower body, Move ignored
    1004 StandUp, 1006 RecoveryStand, 1002 BalanceStand   stand
  Motion stops if no Move arrives for 0.5 s. Every request gets a response.

  Like the robot, nothing is published on /tf. Robot code gets its TF from
  follow_anywhere_ws (same launch on the real robot and here):
    ros2 launch go2_bringup go2_tf.launch.py
  Sensor mounts live in follow_anywhere_ws/src/go2_bringup/config/go2_mounts.yaml;
  this URDF reads the same file. The lidar mount was solved from the bag.
  The D455 position there is an estimate: measure it on the robot.

  Not emulated: /utlidar/height_map_array, /utlidar/range_info,
  /utlidar/voxel_map_compressed, audio, uwb/vui/obstacles_avoid APIs, /lowcmd,
  battery/gnss strings. Battery, foot force and temperatures in /lowstate are
  constants taken from the bag (foot_force is constant on our robot too).

  Sim-internal topics (/sim/*, /cmd_vel, /body_pose, /clock, /sim/tf) are for
  the sim itself; robot code should not use them.


DRIVING FROM follow_anywhere_ws
  With the sim running, on the host:
    cd follow_anywhere_ws && source install/setup.bash
    export ROS_DOMAIN_ID=0
    ros2 run manual_controller keyboard_teleop
  Do NOT use scripts/drive_go2.sh here: it binds CycloneDDS to the robot NIC.
  If the host doesn't see the sim topics, use the same RMW_IMPLEMENTATION on
  both sides (unset it on the host, or set it in docker-compose.yml).

  Test without the host (inside the container):
    ros2 topic pub -r 10 /api/sport/request unitree_api/msg/Request \
      "{header: {identity: {api_id: 1008}}, parameter: '{\"x\": 0.3, \"y\": 0.0, \"z\": 0.0}'}"


TESTING AGAINST THE REAL ROBOT
  The repo is mounted read-only at /repo in the container. With the sim
  running, in a second shell inside the container (cd /ros2_ws/tools):

  Does the sim look like the robot? Compares topics, types, rates, frame ids
  and point cloud layouts with the bag:
    python3 check_interface.py /repo/go2_all_topics_6_10_11_28

  Does the sim move like the robot? Sends the bag's sport commands to the sim
  at their original timing and compares velocities with the robot's:
    python3 replay_commands.py /repo/go2_all_topics_6_10_11_28 --csv /tmp/replay.csv
  Gait parameters to tune against it: go2_description/config/gait.yaml and
  sport_api's velocity_gain / response_time (go2_robot_emulator/sport_api.py).

  Recording a new bag on the robot adds a new reference: pass its directory.


REBUILD AFTER CODE CHANGES
  docker compose up --build


STOP
  Ctrl+C  or  docker compose down


GPU / NO GPU
  By default the container renders with Mesa: on the Intel/AMD integrated
  GPU via /dev/dri. No NVIDIA GPU or nvidia-container-toolkit is needed.

  Pure CPU rendering (llvmpipe), e.g. no /dev/dri or iGPU driver problems:
    LIBGL_ALWAYS_SOFTWARE=1 docker compose up
  (If the host has no /dev/dri at all, also remove the 'devices' block
  from docker-compose.yml.)

  NVIDIA GPU passthrough (faster sensor rendering):
    docker compose -f docker-compose.yml -f docker-compose.gpu.yml up


KNOWN LIMITATIONS
  - Gait quality differs from the physical robot (CHAMP open-source vs Unitree firmware)
  - Camera positions are approximate (verify against physical Go2 CAD for precise TF)
  - Lidar points have synthetic intensity (Gazebo has no reflectivity)
  - Motion vs the robot (tools/replay_commands.py on go2_all_topics_6_10_11_28):
    distance 8.9 m vs 10.4 m, steady speed and turn rate within ~5%, but CHAMP
    takes ~0.3 s to reach a new speed where the robot takes ~0.1 s, so short
    bursts of motion fall short
  - Startup sometimes hangs with the spawner repeating "waiting for service
    /controller_manager/switch_controller" (seen once in ~10 starts).
    Restart the container if the robot is not standing after ~30 s
  - /lowcmd (joint-level control) is not supported
